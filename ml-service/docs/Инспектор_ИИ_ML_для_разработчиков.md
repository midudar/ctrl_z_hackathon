| **Вход** | Папка с документами объекта и реестр файлов `document_manifest.jsonl`. Рядом с реестром — матрица параметров `parameter_catalog_132.jsonl` и схема ответа `submission_schema.json` |

| **Где работает** | Офлайн, без сети и внешних API. GPU не нужен: сканы распознаны заранее, результат лежит в кэше |
| **Сколько идёт** | 1–4 минуты на объект на процессоре ноутбука (замеры — в [п. 4.5](#45-время-и-ресурсы)) |
| **Без чего не работает** | Без реестра `document_manifest.jsonl`: из него берутся стадия, раздел, путь к файлу и `file_id` |
| **Без чего работает хуже** | Без кэша `out/cache`: прогон не падает, но пропадают значения из сканов актов ИД и подписи на чертежах ОВ |

| **Заглушки** | `COMPARISON_IMPOSSIBLE` с пустыми `evidence`, `pd_value` и `rd_value` значит «для параметра нет извлечения». Показывать как «не проверялось системой», а не как «данные несопоставимы» |
| **Первое, что сделать DevOps** | Собрать Docker-образ: он описан, но **ни разу не собирался** (на ноутбуке ML нет Docker). Чек-лист — в [п. 5.5](#55-образ-ни-разу-не-собирался--как-проверить) |
| **Что делает команда, а не ML** | Интерфейс, REST / очередь, загрузку файлов и формирование реестра для новых объектов, хранение решений инспектора, PDF-протокол по Приложению 2 |

## 1. Что ML-часть делает и чего не делает

### Делает

1. **Разбирает комплект.** По реестру определяет стадию (ПД / РД / ИД), дисциплину (КР, АР, ОВ, ВК, ЭОМ…) и шифр каждого
   файла. Из нескольких редакций одного тома («…-КР1», «…-КР1-кор2», «…-КР1-кор3») для ПД и РД оставляет только
   действующую. Номер редакции берётся с титульного листа, имя файла — запасной вариант. ИД не фильтруется: акты друг
   друга не заменяют.
2. **Читает страницы:** текстовый слой PDF, а для сканов и подписей, нарисованных линиями, — заранее распознанный текст
   из кэша.
3. **Извлекает значения** по параметрам, для которых написано извлечение (сейчас их 19 из 132, [п. 13](#13-что-покрыто-сейчас-и-что-будет-меняться)):
   классы бетона и арматуры, толщины, сечения, марки стали, отметку 0.000, огнестойкость, помещения и площади,
   материал канализационных труб, системы вентиляции по помещениям, кабели, светильники, расчётную мощность,
   огнестойкость дверей. Сюда же входят поля актов освидетельствования
   скрытых работ (АОСР) из ИД.
4. **Сравнивает** ПД ↔ РД ↔ ИД по правилам-триггерам матрицы. Например, класс бетона — нарушение только при понижении,
   толщина — только при уменьшении, отметка 0.000 — при любом расхождении.
5. **Страхуется от ложных срабатываний.** Если данных мало или они противоречат друг другу, вместо «нарушения»
   ставится «сравнить нельзя» с пояснением.
6. **Выдаёт ответ** на все 132 параметра. К каждому доказательству — рамка фрагмента на странице (bbox в долях
   видимой страницы, с учётом поворота листа и CropBox).
7. **Проверяет целостность комплекта:** пустые и битые файлы, временные файлы редакторов, дубли, PDF без текста,
   отсутствующие в РД дисциплины, устаревшие редакции, несовпадение шифров.

### Не делает (это задачи команды)

- Интерфейс, REST API, очередь сообщений, авторизация, хранилище файлов.
- Загрузку документов пользователем и **формирование реестра** `document_manifest.jsonl` для нового объекта
  ([п. 3.5](#35-если-объект-загружают-через-интерфейс-что-должен-сделать-backend)).
- Хранение решений инспектора («подтверждаю» / «отклоняю, причина…»). Статус `CONFIRMED_VIOLATION` по ТЗ ставит
  только инспектор.
- PDF / DOCX протокола по образцу Приложения 2. ML отдаёт все данные для него ([п. 10](#10-протокол-по-приложению-2-откуда-брать-данные)).
- OCR во время прогона. Сканы распознаны заранее (PaddleOCR на GPU в Colab), результат лежит в кэше. Код обоих
  проходов OCR есть (`colab/`, `ml/page_kinds.py`, `ml/pages.py`), но в `ml.run` он не встроен.
- Разбор DWG и DOCX: чертежи сверяются по PDF-версиям, они есть у каждого комплекта.
- Обучение моделей: размеченных нарушений всего 10, решение принимают правила матрицы. Готовые модели нужны только
  для чтения (OCR).

## 3. Входные данные

ML-части нужны три вещи: **папка документов**, **папка данных** (реестр, матрица, схема) и **код объекта**
(`object_id`). Пути задаются переменными окружения ([п. 4.2](#42-переменные-окружения)).

### 3.1. Папка документов (`INSPECTOR_DOCS`)

- Путь к файлу = `INSPECTOR_DOCS` / `relative_path` из реестра. Код собирает его сам (`ml.pages.file_path`), руками
  ничего склеивать не нужно.
- Внутреннее устройство папок любое: стадия берётся из реестра, а не из имени папки. У объектов организаторов
  структура разная: у Речникова `ПД / РД / ИД`, у Тюменской РД и ИД лежат в одной папке, у Новослободской папка-дубль
  и «Стадия П».
- В пакете участника это `01_ДОКУМЕНТАЦИЯ/`, а `relative_path` начинается с имени папки объекта:
  `Речников ул. 7-7/РД/2. АР/1. Ниже отметки 0.000 Архитектурно-строительные решения/24-04-23-14-РД-АР0 (Изм.1).pdf`.
- **Файлы только читаются.** Папку можно монтировать read-only (`:ro`).
- На Linux пути регистрозависимы. Проверено: все 416 путей реестра совпадают с файлами на диске побайтно (регистр,
  нормализация Unicode). Не перекодируйте имена при копировании.
- На Windows пути длиннее 260 символов открываются с префиксом `\\?\`, код делает это сам. На Linux ограничения нет.

### 3.2. Реестр файлов `document_manifest.jsonl` (в `INSPECTOR_DATA`) — обязателен

Формат JSON Lines: одна строка — один файл. Файл может содержать строки нескольких объектов, ML берёт строки своего
`object_id`. Реальная строка из пакета:

```json
{"schema_version": "0.1.0", "file_id": "F0328", "object_id": "OBJ-RECHNIKOV-7-7", "corpus": "Речников ул. 7-7",
 "dataset_role": "UNLABELED_POOL", "split": "TEST_HIDDEN",
 "relative_path": "Речников ул. 7-7/РД/2. АР/1. Ниже отметки 0.000 Архитектурно-строительные решения/24-04-23-14-РД-АР0 (Изм.1).pdf",
 "extension": ".pdf", "size_bytes": 6973219,
 "sha256": "3618e640c45d1ddf9a1dcd1815a0a8e0744d669c3f38190d950ddd1cef3679a5",
 "stage": "RD", "section": "AR", "pdf_pages": 23, "annotation_status": "UNLABELED", "exclusion_reason": null,
 "duplicate_group": null, "distribution_status": "INCLUDE", "label_visibility": "ORGANIZER_ONLY"}
```

**Какие поля использует код:**

| Поле | Обязательно | Значения и смысл |
|---|---|---|
| `file_id` | **да** | Уникальный идентификатор файла во всём реестре, строка (в пакете — `F0001`…`F0418`). **Именно он пишется в `evidence[].file_id` ответа.** Менять `file_id` у существующих файлов нельзя: на них ссылаются ответы |
| `object_id` | **да** | Код объекта: `OBJ-RECHNIKOV-7-7`, `OBJ-NOVOSLOBODSKAYA`, `OBJ-TYUMENSKAYA-5-GOLD-SEED`. Используется в имени файла ответа |
| `relative_path` | **да** | Путь от `INSPECTOR_DOCS`, через `/` |
| `extension` | **да** | Расширение с точкой в нижнем регистре: `.pdf`, `.zip`, `.7z`, `.rar`, `.docx`, `.dwg`, `.txt` |
| `stage` | **да** | `PD`, `RD`, `ID` или `RD_ID_MIXED` (РД и ИД в одной папке, как у Тюменской; считается и РД, и ИД). Файлы с другим значением (в пакете один `UNKNOWN`) в сравнении не участвуют |
| `section` | желательно | `KR`, `AR`, `OV`, `VK`, `EOM`, `SS`, `GP`, `POS`, `PB`, `OTHER`. Если неизвестно — `OTHER`: дисциплину код определяет ещё и по шифру в имени файла (`КЖ`, `КМ`, `СВГ`, `АР`, `ОВ`, `ИОС4`, `ВК`, `ЭОМ`, `ПЗ`…). Нужны оба источника: `…_СВГ (1).pdf` в реестре организаторов помечен `OTHER` |
| `sha256` | желательно | SHA-256 файла, 64 символа hex. **По нему ищется кэш распознанных страниц** ([п. 6](#6-кэш-распознанных-страниц)) и дубли в отчёте целостности. Если поля нет, хэш считается из файла при каждом прогоне — на больших объектах это медленно |
| остальные | нет | `corpus`, `split`, `size_bytes`, `pdf_pages`, `annotation_status`… код не читает |

В пакете участника 416 строк: Речников — 213, Новослободская — 145, Тюменская — 58. Стадии: `PD` 172, `ID` 130,
`RD` 103, `RD_ID_MIXED` 10, `UNKNOWN` 1.

### 3.3. Матрица параметров `parameter_catalog_132.jsonl` (в `INSPECTOR_DATA`) — обязательна

132 строки, поля: `parameter_id`, `parameter_code`, `pd_section`, `parameter_name`, `unit`, `source_pd`, `source_rd`,
`source_id`, `trigger`, `criticality`, `matrix_row`, `mapping_status`.

- По ней строится скелет ответа (все 132 параметра).
- Из `source_rd` определяется, каких комплектов РД не хватает (строки «нет документа»).
- `criticality` копируется в ответ: «Критическое (приостановка работ)» — 106 параметров, «Существенное (предписание)» — 26.
- **Интерфейсу она тоже нужна:** названий параметров (`parameter_name`), разделов (`pd_section`), единиц и триггеров
  в ответе нет. Их надо подтягивать из матрицы по `parameter_code`.

### 3.4. Схема ответа `submission_schema.json` (в `INSPECTOR_DATA`) — обязательна

По ней `ml.run` проверяет ответ перед записью. Схема организаторов разрешает лишние поля, поэтому наши дополнительные
поля (`note`, `bbox_norm`, `document_integrity`…) её не нарушают.

### 3.5. Если объект загружают через интерфейс: что должен сделать backend

Для объектов из пакета организаторов реестр уже есть. Для объекта, который пользователь загружает сам, реестр должен
сформировать backend:

1. **Сохранить файлы** в папку документов, например `INSPECTOR_DOCS/<папка объекта>/<как загрузил пользователь>`.
   Исходные имена файлов лучше сохранить: по шифру в имени (`…-РД-КЖ2.pdf`) определяется дисциплина и редакция.
2. **Спросить у пользователя стадию каждого файла** (ПД / РД / ИД) или папки целиком. Это критично: ML **не
   определяет стадию по содержимому**, только по полю `stage`.
3. **Посчитать SHA-256** каждого файла. Он же пригодится для поиска дублей при загрузке.
4. **Дописать строки** в `INSPECTOR_DATA/document_manifest.jsonl`: `file_id` (уникальный, например `U-<uuid>` или
   сквозной номер), `object_id`, `relative_path`, `extension`, `stage`, `section` (из выбора пользователя или `OTHER`),
   `sha256`.
5. Положить рядом `parameter_catalog_132.jsonl` и `submission_schema.json` (без изменений из пакета).
6. Запустить `python -m ml.run <object_id>`.

Тонкость: у нового объекта кэша распознанных страниц нет. Всё, что есть в текстовом слое PDF (почти вся ПД и РД),
прочитается. Значения со сканов (акты ИД) — нет: OCR в прогон не встроен ([п. 14](#14-ограничения-риски-и-открытые-вопросы)).

### 3.6. Какие файлы как обрабатываются

| Тип | Что делает ML |
|---|---|
| `.pdf` с текстовым слоем | читает текст, координаты слов и векторную графику (линии, слои CAD) |
| `.pdf`-скан (нет текстового слоя) | берёт распознанный текст из кэша, если он есть; иначе страница пропускается |
| `.zip`, `.docx` | только отчёт целостности: список файлов внутри (временные `.bak`, `~$…`, `.log`), битый ли архив |
| `.7z`, `.rar` | то же, через `bsdtar` (в Linux — пакет `libarchive-tools`, в образ добавлен) |
| `.dwg`, прочее | не обрабатывается |

Редакции: для ПД и РД из группы файлов с одним шифром берётся последняя (по титулу: «Корректировка №3», год; запасной
вариант — «кор3», «Изм 2» в имени). Отброшенные редакции перечислены в отчёте целостности
(`SUPERSEDED_REVISIONS_EXCLUDED`). У Речникова так исключено 38 устаревших томов ПД из 89.

## 4. Запуск

### 4.1. Командная строка

Запуск — из папки ML-части (`ml-service/`), модулем:

```bash
python -m ml.run OBJ-RECHNIKOV-7-7                          # → $INSPECTOR_OUT/submission_OBJ-RECHNIKOV-7-7.json
python -m ml.run OBJ-RECHNIKOV-7-7 --out /output/answer.json  # свой путь к ответу
python -m ml.run                                            # все объекты из реестра по очереди
```

- Аргумент — `object_id` из реестра. Без аргумента обрабатываются все объекты реестра.
- `--out` задаёт путь к файлу ответа, только вместе с одним объектом. Отчёт целостности кладётся **рядом с ответом**:
  `<папка --out>/integrity_<object_id>.json`.

### 4.2. Переменные окружения

| Переменная | По умолчанию (локально) | В Docker-образе | Что это |
|---|---|---|---|
| `INSPECTOR_ROOT` | папка над `ml/` | `/app` | корень проекта |
| `INSPECTOR_DOCS` | `01_ПАКЕТ/…/01_ДОКУМЕНТАЦИЯ` | `/input/docs` | папка документов ([п. 3.1](#31-папка-документов-inspector_docs)) |
| `INSPECTOR_DATA` | `01_ПАКЕТ/…/02_ФОРМАТ_ДАННЫХ_И_ПРИМЕРЫ/data` | `/input/data` | реестр, матрица, схема |
| `INSPECTOR_OUT` | `out` | `/output` | куда писать ответы и отчёты целостности |
| `INSPECTOR_CACHE` | `$INSPECTOR_OUT/cache` | `/app/cache` | кэш распознанных страниц ([п. 6](#6-кэш-распознанных-страниц)). Отдельно от `OUT`, чтобы папка вывода на стенде оставалась пустой |
| `INSPECTOR_MODELS` | `models` | не задана → `/app/models` | модели EasyOCR (`models/easyocr`). `ml.run` их не загружает, они нужны только командам OCR |
| `INSPECTOR_OCR_GPU` | авто | — | `0` / `1` — принудительно CPU / GPU для команд OCR (`python -m ml.pages`). На `ml.run` не влияет |
| `INSPECTOR_FONT`, `INSPECTOR_FONT_BOLD` | DejaVu / Arial | DejaVu из `fonts-dejavu-core` | шрифт с кириллицей для PDF-карточек (`ml.review_pdf`, `ml.slides_pdf`). На `ml.run` не влияет |
| `PYTHONIOENCODING` | — | `utf-8` | обязательно на Windows, иначе кириллица в логах ломается |

**Важно:** пути читаются **один раз при импорте** `ml.paths`. Если запускаете ML из своего Python-кода, задайте
переменные **до** `import ml…` ([п. 4.4](#44-вызов-из-python)).

### 4.3. Что пишется в лог и коды возврата

Лог идёт в stdout построчно, без буферизации в образе (`PYTHONUNBUFFERED=1`). Реальный прогон Речникова:

```
=== OBJ-RECHNIKOV-7-7
  PD: файлов по дисциплинам 13
  RD: файлов по дисциплинам 36
  ID: файлов по дисциплинам 0
  трек КР и ИД: 13 проверок за 98 с
  трек ОВ: чертежи этого объекта не заданы, пропускаю
  трек ОВ: 0 проверок за 0 с
  трек пожарные характеристики: 2 проверок за 50 с
  трек экспликации помещений: 2 проверок за 0 с
  трек сталь металлопроката: 2 проверок за 9 с
  трек канализационные трубы: 2 проверок за 8 с
  трек электрика: кабели, свет, мощность: 3 проверок за 17 с
  трек огнестойкость дверей: 1 проверок за 12 с
  рамки доказательств: 54 из 54 за 0 с
  целостность комплекта: дефектов 4 за 47 с
/output/submission_OBJ-RECHNIKOV-7-7.json: строк 141, ошибок проверки 0, за 242 с
  COMPARISON_IMPOSSIBLE  92
  MISSING_DOCUMENT       32
  NO_VIOLATION           16
  VIOLATION_PRESENT      1
```

(«ID: файлов по дисциплинам 0» — нормально: для ИД дисциплина не определяется, акты разбираются отдельно.)

**Поведение при ошибках:**
- Треки независимы. Если один трек падает, в stderr пишется `трек …: ОШИБКА` с трассировкой, остальные работают
  дальше, а на месте упавшего в ответе остаются заглушки. **Ответ пишется всегда.**
- Если ответ не прошёл проверку (схема, дубли ключей, `VIOLATION_PRESENT` без доказательств, не все 132 параметра),
  ошибки печатаются в stderr как `ошибка ответа: …`, ответ всё равно пишется, код возврата — **1**.
- Объекта нет в реестре — сообщение `объекта … нет в реестре; есть: …`, код возврата 1, ответ не пишется.
- Всё хорошо — код возврата **0**.

MuPDF иногда пишет в stderr `MuPDF error: syntax error: missing font descriptor`. Это предупреждения о шрифтах внутри
PDF организаторов, на результат они не влияют. В логах сервиса их можно отфильтровать.

### 4.4. Вызов из Python

```python
import os
os.environ["INSPECTOR_DOCS"] = "/data/docs"          # ДО импорта ml
os.environ["INSPECTOR_DATA"] = "/data/meta"
os.environ["INSPECTOR_OUT"] = "/data/out"
os.environ["INSPECTOR_CACHE"] = "/app/cache"

from ml.run import run
result, errors = run("OBJ-RECHNIKOV-7-7", out_path="/data/out/submission_OBJ-RECHNIKOV-7-7.json")
# result — dict ответа (то же, что записано в файл), errors — список строк ошибок проверки ([] — всё хорошо)
```

Надёжнее запускать отдельным процессом (`subprocess` / `docker run`). Модули держат кэши в памяти (`lru_cache`),
поэтому долгоживущий процесс с разными наборами документов лучше не использовать.

### 4.5. Время и ресурсы

Замеры на ноутбуке ML: CPU, без GPU, один процесс, кэш на месте.

| Объект | Файлов в реестре | Время `ml.run` |
|---|---|---|
| Новослободская (обучающий) | 145 | ~1 мин (62 с) |
| Тюменская (обучающий) | 58 | 2–3,5 мин (128–196 с в разных прогонах; дольше всего трек ОВ — большие листы чертежей) |
| Речников (тестовый) | 213 | ~4 мин (234 с, с треками электрики и дверей). Без кэша разбора экспликаций — ещё ~1,5 мин |

- GPU `ml.run` не использует.
- Память не замерялась. Больше всего её берёт PyMuPDF на листах формата A0 (до 165 тыс. графических элементов на лист).
- **Разные объекты можно обрабатывать параллельно** в разных процессах. **Один и тот же объект одновременно — нельзя:**
  оба процесса пишут один файл ответа и одни файлы кэша.
- Нормативы ТЗ (раздел 11): «сравнение 132 параметров — 2 мин», «OCR PDF до 500 страниц — 10 мин». Наше время
  включает чтение тысяч страниц. На процессоре ноутбука мы укладываемся не везде; на стенде (24 ядра, H100) должно быть
  быстрее, но это не замерялось. Как организаторы будут мерить норматив — открытый вопрос.

## 5. Docker-образ

### 5.1. Сборка

```bash
git clone -b ml git@github.com:midudar/ctrl_z_hackathon.git && cd ctrl_z_hackathon/ml-service
# inspector_ml_assets.zip — из GitHub Releases репозитория (п. 2.2)
unzip inspector_ml_assets.zip -d .        # появятся out/cache/ и models/easyocr/
docker build -t inspector-ml .
```

Контекст сборки ограничен `.dockerignore`: в него попадают только `ml/`, `models/easyocr/`, `requirements.txt` и
`out/cache/`. Это важно: на машине ML в папке проекта ~42 ГБ данных организаторов, без `.dockerignore` сборка
потащила бы их все.

### 5.2. Запуск

```bash
docker run --rm --gpus all \
  -v /path/to/01_ДОКУМЕНТАЦИЯ:/input/docs:ro \
  -v /path/to/data:/input/data:ro \
  -v /path/to/output:/output \
  inspector-ml OBJ-RECHNIKOV-7-7
```

- `/input/docs` — папка документов (`01_ДОКУМЕНТАЦИЯ` из пакета), пути внутри — как `relative_path` реестра.
- `/input/data` — `document_manifest.jsonl`, `parameter_catalog_132.jsonl`, `submission_schema.json`.
- `/output` — сюда появятся `submission_<объект>.json` и `integrity_<объект>.json`. Больше ничего туда не пишется:
  кэш живёт в `/app/cache` внутри контейнера.
- Аргумент после имени образа — `object_id`. Без него обрабатываются все объекты реестра.
- `--gpus all` сейчас не обязателен (GPU не используется), но и не мешает. Стенд жюри — Linux + Docker +
  NVIDIA Container Toolkit, 1 × H100.

### 5.3. Что внутри образа

| Слой | Откуда |
|---|---|
| База `pytorch/pytorch:2.4.1-cuda12.1-cudnn9-runtime` | CUDA runtime, cuDNN, torch. **Драйвер NVIDIA в образ класть нельзя** (требование организаторов): он приходит с хоста |
| `fonts-dejavu-core` | кириллица в PDF-карточках |
| `libarchive-tools` | `bsdtar` — список файлов внутри `.7z` и `.rar` для отчёта целостности (у Речникова так находятся временные файлы в `F0339` .rar и `F0412` .7z) |
| `pip install -r requirements.txt` | pymupdf, easyocr, jsonschema, numpy, opencv-python-headless |
| `ml/` → `/app/ml` | код |
| `models/easyocr/` → `/app/models/easyocr` | веса EasyOCR (~94 МБ; `ml.run` их не грузит, они для команд OCR) |
| `out/cache/` → `/app/cache` | **кэш распознанных страниц** ([п. 6](#6-кэш-распознанных-страниц)) |
| `ENV` | `PYTHONIOENCODING=utf-8`, `PYTHONUNBUFFERED=1`, `INSPECTOR_ROOT=/app`, `INSPECTOR_DOCS=/input/docs`, `INSPECTOR_DATA=/input/data`, `INSPECTOR_OUT=/output`, `INSPECTOR_CACHE=/app/cache` |
| `ENTRYPOINT` | `python -m ml.run` |

Требования стенда (ответ организаторов): подключаться к своему удалённому API запрещено, Claude API и любые облачные
модели в решении нельзя, всё должно работать внутри контейнера. ML-часть этому соответствует: сеть ей не нужна.

### 5.4. Если нужен свой entrypoint

Если сервис запускает ML не как отдельный контейнер на объект, а как воркер (см. [п. 11](#11-встраивание-в-стек-из-тз-rest-rabbitmq)),
`ENTRYPOINT` можно заменить. Команда та же: `python -m ml.run <object_id> [--out путь]`, рабочая папка — `/app`.

### 5.5. Образ ни разу не собирался — как проверить

На ноутбуке ML нет Docker, поэтому проверены только версии зависимостей и сам `ml.run` локально (в том числе с
`INSPECTOR_OUT` и `INSPECTOR_CACHE` в разных папках, как на стенде). Порядок проверки:

1. Распаковать `inspector_ml_assets.zip` в папку ML-части, `docker build`. Возможные проблемы: скачивание базового
   образа (несколько ГБ), колёса `pymupdf` / `opencv` под платформу.
2. **Быстрый прогон — Новослободская** (~1 мин). Сравнить результат с эталонным примером из репозитория:
   ```bash
   docker run --rm -v "$PWD/01_ДОКУМЕНТАЦИЯ:/input/docs:ro" -v "$PWD/data:/input/data:ro" \
              -v "$PWD/check:/output" inspector-ml OBJ-NOVOSLOBODSKAYA
   python - <<'EOF'
   import json
   a = json.load(open("out/submission_OBJ-NOVOSLOBODSKAYA.json", encoding="utf-8"))
   b = json.load(open("check/submission_OBJ-NOVOSLOBODSKAYA.json", encoding="utf-8"))
   key = lambda c: (c["parameter_code"], c["location"])
   A, B = {key(c): c for c in a["checks"]}, {key(c): c for c in b["checks"]}
   print("строки совпадают:", A == B, "| целостность совпадает:", a["document_integrity"] == b["document_integrity"])
   EOF
   ```
   Строки должны совпасть полностью, включая рамки. Если разошлись только `inside_archives` в целостности — проверьте,
   что `bsdtar` есть в образе.
3. **Речников** (~3 мин) — так же сравнить с `out/submission_OBJ-RECHNIKOV-7-7.json`. Если у строк KR-055 / KR-057
   пропали `id_value` (значения из актов), значит кэш не подхватился: проверьте `/app/cache` и совпадение `sha256`
   в реестре с файлами ([п. 6](#6-кэш-распознанных-страниц)).
4. Проверить, что в `/output` лежат ровно два файла на объект.
5. Проверить запуск без `--gpus` (на случай, если GPU на стенде будет занят другими командами).

## 6. Кэш распознанных страниц

### Зачем он нужен

- Почти вся ИД тестового объекта (Речников) — **сканы**: 8 324 страницы, текстового слоя нет.
- Подписи на чертежах РД ОВ нарисованы **линиями** (шрифт CAD экспортирован контурами), поэтому их тоже можно
  прочитать только распознаванием.
- Распознавание сделано заранее, на GPU в Google Colab, и сохранено в кэш:
  - PaddleOCR — 910 нужных страниц ИД Речникова (бланки актов и реестры приложений);
  - EasyOCR — листы ОВ Тюменской.

### Как устроен

- Ключ — **SHA-256 файла** (первые 16 hex-символов, `sha16`), берётся из поля `sha256` реестра, а при его отсутствии
  считается по файлу.
- Структура:
  ```
  cache/
    <sha16>/<номер страницы>.json        токены текстового слоя (заполняется сам при прогоне)
    <sha16>/<номер страницы>_ocr.json    распознанный текст страницы: токены с рамками и уверенностью, источник
                                         (ocr_source: paddle / easyocr)
    explication/<sha16>_v5.json          разбор таблиц экспликаций помещений (минуты на лист A0 без кэша)
  ```
- **Папка кэша должна быть доступна на запись:** при прогоне туда дописываются токены текстового слоя и разбор таблиц.
  В контейнере она по умолчанию доступна. Если монтируете её томом, не делайте `:ro`.

### Что будет без кэша или при промахе

| Ситуация | Последствие |
|---|---|
| Кэша нет вообще | прогон не падает. У Речникова пропадут значения ИД (`id_value` у KR-055 / KR-057, страницы актов в `evidence`), у Тюменской трек ОВ почти ничего не найдёт (подписи-линии не прочитать), экспликации Речникова будут разбираться на ~1,5 мин дольше |
| Файлы на стенде побайтно другие (пересохранены, другие версии) | промах по ключу — то же самое для этих файлов |
| В реестре стенда нет `sha256` | хэши считаются из файлов — медленнее, но кэш найдётся, если файлы те же |

## 7. Выход: файл ответа

### 7.1. Файлы

| Файл | Где | Что |
|---|---|---|
| `submission_<object_id>.json` | `INSPECTOR_OUT` или путь `--out` | ответ по всем 132 параметрам |
| `integrity_<object_id>.json` | рядом с ответом | полный отчёт о целостности комплекта |

Кодировка UTF-8, отступ 2 пробела, кириллица не экранируется (`ensure_ascii=False`). Каждый прогон перезаписывает
файлы целиком. Ответ зависит только от входных данных и кода: при тех же документах и том же кэше он воспроизводится
байт в байт.

### 7.2. Верхний уровень

```json
{
  "object_id": "OBJ-RECHNIKOV-7-7",
  "checks": [ ... строки по параметрам ... ],
  "document_integrity": { "summary": {...}, "findings": [...] }
}
```

- `object_id` и `checks` — по схеме организаторов.
- `document_integrity` — наше дополнение, краткая версия отчёта целостности ([п. 8](#8-выход-отчёт-о-целостности-комплекта)).

### 7.3. Строка `checks[]`

| Поле | Тип | Всегда есть | Смысл |
|---|---|---|---|
| `parameter_code` | string | да | Код параметра из матрицы: `KR-057`, `PZ-003`, `IOS4-078`. Есть один код вне матрицы — `FREE-HEATING-001` (тёплые полы, «свободный поиск» из эталона организаторов) |
| `location` | string | да | Где: номер помещения, название конструкции, система, «Объект» или `""` ([п. 7.7](#77-location-формат-места)). **Ключ строки — пара `(parameter_code, location)`, она уникальна** |
| `violation_label` | enum | да | `VIOLATION_PRESENT` / `NO_VIOLATION` / `MISSING_DOCUMENT` / `COMPARISON_IMPOSSIBLE` ([п. 7.5](#75-violation_label-метки)) |
| `protocol_status` | enum | да | `CRITICAL` / `WARNING` / `OK` / `RD_MISSING` / `PD_MISSING` / `ID_MISSING` / `COMPARISON_IMPOSSIBLE` ([п. 7.6](#76-protocol_status-статус-для-протокола)) |
| `criticality` | string | да | Из матрицы, дословно: «Критическое (приостановка работ)» или «Существенное (предписание)». У `FREE-HEATING-001` (вне матрицы) — «Существенное (предписание)», как в эталоне организаторов |
| `pd_value`, `rd_value`, `id_value` | string \| null | да | Значения на стадиях, **как строки для показа человеку**: `"B30/B35"`, `"200/250/600 мм"`, `"чугун, ПП"`, `"В2: В2.7, В2.8, В2.9"`, `"1349,70 м² (2 пом.)"`. `null` — значение на этой стадии не найдено или не извлекается |
| `evidence` | array | да | Доказательства: файл, страница, рамка ([п. 7.4](#74-evidence-доказательства-и-рамки)). У заглушек — пустой массив |
| `note` | string | нет | Пояснение для инспектора, если есть: «в РД нет комплекта ОВ», «изменены площади 2 помещений…», «К1: чугун из ПД в РД сохранены, ПВХ не добавлен» |

Порядок строк в `checks` смысла не несёт: сначала скелет, потом найденные строки треков. **Сортируйте в интерфейсе
сами**, например по `parameter_id` из матрицы, затем по `location`.

У одного параметра может быть **несколько строк** с разными `location`. Например, KR-055 (класс бетона) — по одной на
конструкцию, IOS4-078 — по одной на помещение, PZ-003 — итог по объекту плюс строки по помещениям и этажам. Поэтому
строк в ответе больше 132 (141–157).

### 7.4. `evidence[]`: доказательства и рамки

```json
{"stage": "PD", "file_id": "F0105", "pdf_page_number": 13,
 "bbox_norm": [0.1669, 0.6708, 0.7817, 0.6866], "bbox_source": "text_layer",
 "fragment": "вязанными арматурными каркасами, основная рабочая арматура А400,"}
```

| Поле | Смысл |
|---|---|
| `stage` | `PD` / `RD` / `ID` — к какой стадии относится страница |
| `file_id` | файл из реестра. Имя и путь для показа — по реестру (`relative_path`) |
| `pdf_page_number` | номер страницы **PDF**, с 1. Это не номер листа в штампе: лист 26 тома может лежать на странице 104 |
| `bbox_norm` | рамка фрагмента `[x0, y0, x1, y1]` в **долях видимой страницы**, начало — левый верхний угол. CropBox, MediaBox и поворот страницы (`/Rotate`) уже учтены. `null` — фрагмент не найден, показывать страницу целиком (сейчас рамки есть у всех 156 ссылок трёх объектов) |
| `bbox_source` | `text_layer` (из текстового слоя) или `ocr` (со скана, по распознанному тексту) |
| `fragment` | текст внутри рамки (до 200 символов) — подпись к подсветке |

- Порядок: сначала ПД, потом РД, потом ИД.
- На одну стадию бывает **несколько страниц**: у КР до 3 страниц РД, например текст общих указаний, спецификация
  и лист чертежа. Показывайте все.
- У строки `COMPARISON_IMPOSSIBLE` бывает доказательство только одной стадии: значение нашлось в РД, а в ПД нет.

**Как нарисовать рамку.** Отрисуйте страницу так, как её видит человек, и умножьте доли на размер картинки:

```js
// PDF.js: viewport уже учитывает /Rotate и CropBox
const page = await pdf.getPage(ev.pdf_page_number);
const viewport = page.getViewport({ scale });
// ... отрисовка страницы в canvas размером viewport.width × viewport.height ...
const [x0, y0, x1, y1] = ev.bbox_norm;
ctx.strokeRect(x0 * viewport.width, y0 * viewport.height,
               (x1 - x0) * viewport.width, (y1 - y0) * viewport.height);
```

В Python (PyMuPDF): `pix = page.get_pixmap(dpi=150)` — это уже видимая страница, рамка равна
`[x0*pix.width, y0*pix.height, x1*pix.width, y1*pix.height]`. Готовая реализация с отрисовкой в PNG —
`python -m ml.evidence_boxes <ответ.json> --png <папка>`.

Рамки проверены глазами на трудных случаях: лист с поворотом 270°, CropBox со сдвигом 3604 pt, сдвинутый MediaBox,
повёрнутые листы РД, сканы актов (OCR), номера помещений на планах.

### 7.5. `violation_label`: метки

| Метка | Смысл | Как показывать |
|---|---|---|
| `VIOLATION_PRESENT` | Найдено расхождение по триггеру матрицы, есть доказательства | **«Кандидат в нарушения»** — на решение инспектора: подтвердить / отклонить с причиной |
| `NO_VIOLATION` | Сверили — расхождения нет. Значения и доказательства есть | «Проверено, нарушений нет» |
| `MISSING_DOCUMENT` | Нет нужного документа: в РД нет комплекта нужной марки или нет стадии целиком. Причина — в `note` | «Не хватает документа» + `note` |
| `COMPARISON_IMPOSSIBLE` **с пустыми** `evidence`, `pd_value`, `rd_value` | **Заглушка**: для параметра нет извлечения | **«Не проверялось системой»**. Не «данные несопоставимы» |
| `COMPARISON_IMPOSSIBLE` с доказательствами | Сравнили, но уверенности нет: значение только на одной стадии, сработала страховка, документы РД расходятся между собой | «Нужна ручная проверка» + `note` |

Как отличить заглушку в коде: `label == "COMPARISON_IMPOSSIBLE" && evidence.length == 0 && pd_value == null && rd_value == null`.

Соответствие статусам ТЗ (раздел 9.2):

| Статус ТЗ | `violation_label` |
|---|---|
| `CANDIDATE` | `VIOLATION_PRESENT` |
| `NEGATIVE_VERIFIED` | `NO_VIOLATION` |
| `MISSING_EVIDENCE` | `MISSING_DOCUMENT` |
| `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED` | `COMPARISON_IMPOSSIBLE` |
| `NOT_APPLICABLE`, `SUSPICION` | в `checks` не выводятся |
| `CONFIRMED_VIOLATION` | ставит **только инспектор** в интерфейсе, ML его не выдаёт |

Поле из схемы организаторов (осталось от ТЗ ред. 1.0). ML заполняет его по метке:

| `violation_label` | `protocol_status` |
|---|---|
| `VIOLATION_PRESENT`, критический параметр | `CRITICAL` |
| `VIOLATION_PRESENT`, существенный параметр | `WARNING` |
| `NO_VIOLATION` | `OK` |
| `MISSING_DOCUMENT` | `RD_MISSING` / `PD_MISSING` / `ID_MISSING` — какой стадии не хватает (по реестру или по `note` трека). Сейчас на практике встречается `RD_MISSING` |
| `COMPARISON_IMPOSSIBLE` | `COMPARISON_IMPOSSIBLE` |

### 7.8. Значения: как читать

- Значения — **строки для человека**, не для вычислений. Несколько значений одной стадии — через `/` или `, `.
- Десятичный разделитель как в документе: `"122.65"` у отметки 0.000, `"1349,70 м²"` у площадей.
- Классы бетона приведены к виду `B30` (латинская B, как в эталоне организаторов), арматура — `А500С`.
- Трек ОВ: `"В2: В2.7, В2.8, В2.9"` = система: ветки.
- Числовое «отклонение» отдельным полем не выдаётся. Суть расхождения — в значениях и в `note`.

## 8. Выход: отчёт о целостности комплекта

Проверки не о проектных решениях, а о **самих файлах комплекта**. Типы взяты из пилотной разметки организаторов (там
37 из 48 записей — такие дефекты). Похоже, за это дают 10 баллов технической оценки («document integrity and split
handling»), точный смысл организаторы не раскрыли. Для протокола это готовый материал раздела «Статус загрузки
документов».

### 8.1. Два вида

- **Полный** — `integrity_<object_id>.json`: `{"object_id", "summary", "findings"}`, списки файлов полностью.
- **Краткий** — ключ `document_integrity` в ответе: `{"summary", "findings"}`, каждый список обрезан до 20 элементов.

`summary`: `{"files": 213, "pdf": 164, "stages": ["ID", "PD", "RD"], "findings": 4}` — сколько файлов у объекта в
реестре, из них PDF, какие стадии есть, сколько найдено дефектов.

### 8.2. Находка

```json
{"type": "PDF_WITHOUT_MACHINE_READABLE_TEXT", "severity": "MEDIUM",
 "title": "ID: у 13 из 31 PDF на первой странице нет текстового слоя — нужен OCR",
 "count": 13, "file_ids": ["F0208", "F0209", "..."], "stage": "ID"}
```

Всегда есть `type`, `severity`, `title` (готовая фраза для человека), `count` и `file_ids`. Дополнительные поля
зависят от типа:

| `type` | `severity` | Что значит | Доп. поля |
|---|---|---|---|
| `UNREADABLE_OR_EMPTY_SOURCE_FILE` | CRITICAL | файл пустой или не открывается (PDF, архив) | — |
| `TEMPORARY_EDITOR_ARTIFACTS` | MEDIUM | временные и резервные файлы редакторов (`~$…`, `.bak`, `.dwl`, `.tmp`, `.log`), в том числе **внутри архивов** | `inside_archives` (`"F0326:Генплан.bak"`), `inside_archives_count` |
| `PDF_WITHOUT_MACHINE_READABLE_TEXT` | MEDIUM | у PDF нет текстового слоя на первой странице — нужен OCR | `stage` |
| `EXACT_DUPLICATES_WITHIN_STAGE` | MEDIUM | побайтные дубли (одинаковый SHA-256) внутри стадии | — |
| `EXACT_DUPLICATES_ACROSS_STAGES` | HIGH | одинаковые файлы в разных стадиях | — |
| `EXACT_DUPLICATES_ACROSS_OBJECTS` | HIGH | одинаковые файлы в разных объектах | — |
| `MISSING_COMPARISON_STAGE` | HIGH | у объекта нет стадии целиком (ПД, РД или ИД) | `stages` |
| `DISCIPLINE_MISSING_IN_RD` | HIGH | раздел есть в ПД, а комплектов РД этой марки нет | `disciplines` (`["ОВ", "СС"]`) |
| `SUPERSEDED_REVISIONS_EXCLUDED` | INFO | устаревшие редакции исключены из сравнения (не дефект, а справка) | `stage` |
| `REVISION_CONFLICT` | HIGH | две действующие редакции одного шифра с разным содержимым → `CLARIFICATION_REQUIRED` | `stage` |
| `FILENAME_TITLE_CODE_MISMATCH` | HIGH | шифр в имени файла не совпадает с шифром на титуле | `details` (`file_id`, `in_name`, `on_title`) |
| `ID_REFERENCED_DESIGN_NOT_IN_PACKAGE` | HIGH | акт ИД ссылается на проект (марку РД), которого нет в пакете | `examples` (`file_id`, `design`) |

У Речникова сейчас четыре находки:
- 6 временных файлов внутри архивов РД;
- у 13 из 31 PDF ИД нет текстового слоя;
- в ПД есть разделы ОВ и СС, а в РД их нет;
- 38 устаревших редакций ПД исключены.

**Известная косметическая проблема:** имена файлов внутри `.7z` и `.rar` с кириллицей в `inside_archives` на Windows
выходят с «�» (`"F0339:01-07.23-14-��-��0.bak"`). Это кодировка вывода `tar.exe`. В Linux-образе с `bsdtar` и UTF-8
должно быть нормально, но это не проверялось. Если имена поломаны — показывайте `file_id` архива и расширение.

## 9. Как показывать результат в интерфейсе

Это рекомендации ML-части; окончательно решает тот, кто делает интерфейс.

### 9.1. Сводка по объекту

- Счётчики меток: кандидаты / нет нарушения / не хватает документов / нужна ручная проверка / не проверялось
  системой. Последние два — `COMPARISON_IMPOSSIBLE` с доказательствами и без.
- Кандидаты разделить на критические (`CRITICAL`) и существенные (`WARNING`).
- Блок «Комплект документов» — из `document_integrity`: сколько файлов, какие стадии, список находок с `severity`.

### 9.2. Таблица параметров

- Строка = строка `checks`. Колонки:
  - раздел (`pd_section` из матрицы);
  - код и название параметра (`parameter_name` из матрицы);
  - место (`location`);
  - ПД / РД / ИД (значения);
  - метка;
  - критичность.
- Для `FREE-HEATING-001` в матрице строки нет. Название — «Тёплые полы (свободный поиск, вне матрицы)».
- Сортировка по порядку матрицы (`parameter_id`), внутри — по `location`.
- Фильтры: по метке, по критичности, по разделу, «только с доказательствами».
- Пустой `location` показывать как «—».

### 9.3. Карточка кандидата (главный экран для инспектора)

1. Параметр: код, название, раздел, критичность, триггер из матрицы (`trigger`) — почему это считается нарушением.
2. Место (`location`) и значения ПД / РД / ИД рядом, чтобы было видно, что изменилось.
3. Пояснение (`note`), если есть.
4. Доказательства: по каждой ссылке — имя файла (по реестру) и страница, картинка страницы с подсвеченной рамкой
   (`bbox_norm`) и подписью (`fragment`). ПД и РД удобно показывать рядом.
5. Решение инспектора: «Подтвердить» / «Отклонить» + причина (ТЗ требует причину отклонения) + комментарий.

**Решения храните отдельно** от файла ответа, по ключу `object_id + parameter_code + location`. Файл ответа
перезаписывается при каждом прогоне, а ключ между прогонами стабилен.

### 9.4. Строки без кандидата

- `NO_VIOLATION` — полезно показывать с доказательствами: инспектор видит, что именно сверено.
- `COMPARISON_IMPOSSIBLE` с доказательствами — «нужна ручная проверка», показать `note` и найденную страницу.
- `MISSING_DOCUMENT` — «не хватает документа: `note`».
- Заглушки — серым, «не проверялось системой». Их больше всего, и это честно: извлечение написано не для всех
  параметров.

### 9.5. Если `bbox_norm` = `null`

Показывать страницу целиком, без рамки. Сейчас таких ссылок нет, но формат их допускает.

## 11. Встраивание в стек из ТЗ (REST, RabbitMQ)

ТЗ (раздел 1.5) предписывает React, Node.js, Python 3.11+, REST и RabbitMQ. ML-часть — обычная Python-команда без
состояния между запусками, поэтому её удобно запускать **воркером по сообщению из очереди**. Это предложение ML, не
требование:

```
React ──REST──▶ Node.js API ──(publish)──▶ RabbitMQ: очередь "inspect"
                                                 │  {"object_id": "...", "job_id": "..."}
                                                 ▼
                                   Python-воркер (образ inspector-ml, свой entrypoint)
                                   1. дописать реестр объекта (если новый) — п. 3.5
                                   2. python -m ml.run <object_id> --out /output/<job_id>/submission.json
                                   3. publish в "inspect.done":
                                      {"job_id", "object_id", "exit_code",
                                       "submission": ".../submission.json",
                                       "integrity": ".../integrity_<object_id>.json"}
                                                 │
Node.js API ◀──(consume)── "inspect.done" ── читает JSON, кладёт в БД, отдаёт фронту
```

- **Таймаут** задачи — с запасом, 15–20 минут на объект.
- **Параллельность:** разные объекты — параллельно (отдельные процессы или контейнеры), один объект — строго по одному.
- **Повтор** безопасен: прогон перезаписывает свои файлы целиком.
- **Статус задачи:** код возврата 0 — ответ валиден; 1 — ответ записан, но с ошибками проверки (смотреть stderr);
  другой — упал весь прогон.
- **Кэш и Redis.** ТЗ 9.1 упоминает кэш в Redis. У нас кэш файловый (ключ — SHA-256 файла, как требует ТЗ). Если
  Redis нужен формально, его можно поставить перед вызовом ML (кэшировать ответ по набору SHA-256 файлов объекта),
  не трогая ML.

## 12. Вспомогательные команды

Все запускаются из папки ML-части, `PYTHONIOENCODING=utf-8` на Windows.

| Команда | Что делает |
|---|---|
| `python -m ml.submission validate out/submission_<объект>.json` | проверка ответа: схема, дубли ключей, кандидаты без доказательств, все ли 132 параметра |
| `python -m ml.evidence_boxes <ответ.json> --png <папка>` | дописать рамки в готовый ответ и нарисовать их на картинках страниц — для проверки глазами |
| `python -m ml.review_pdf <объект> <код>:<место> …` | PDF-карточки кандидатов (фрагменты ПД / РД с подсветкой), например `python -m ml.review_pdf OBJ-TYUMENSKAYA-5-GOLD-SEED IOS4-078:140` |
| `python -m ml.integrity <объект>` | только отчёт целостности → `out/integrity_<объект>.json` |
| `python -m ml.registry <объект> KR` | какие файлы объекта отнесены к дисциплине (KR / OV / AR / PZ), уже без устаревших редакций |
| `python -m ml.revisions <объект> PD` | разбор редакций: какие тома одного шифра лежат рядом и какой действующий |
| `python -m ml.eval <ответ1.json> <ответ2.json>` | метрики по эталону организаторов (только обучающие объекты; нужен `TRAIN_data/public_gold_checks.jsonl`) |
| `python -m ml.slides_pdf` | пересобрать материалы для презентации |

**Не использовать для итогового ответа** `python -m ml.concrete … compare` и `python -m ml.rooms …`: они перезаписывают
`out/submission_<объект>.json` ответом одного трека. Итоговый ответ — только `ml.run`.

## 14. Ограничения, риски и открытые вопросы

### Ограничения ML-части

- **Покрытие:** извлечение есть для 19 параметров из 132. Остальные честно помечены «не проверялось системой».
- **OCR не встроен в прогон.** Сканы распознаны заранее и лежат в кэше. Для нового объекта со сканами значения из
  сканов не извлекутся. Код распознавания есть (`colab/`, `ml/page_kinds.py`, `ml/pages.py`: дешёвый проход по верхней
  части страниц → тип страницы → полный OCR нужных страниц). Встроить его в `ml.run` на GPU стенда — отдельная задача.
- **Трек ОВ** знает файлы чертежей только Тюменской (заданы в коде). На других объектах он не запускается.
- **Стадия файла — только из реестра.** По содержимому ML её не определяет.
- **Sentence-BERT** (`all-MiniLM-L6-v2`, требование ТЗ 9.1) пока не используется: извлечение — на правилах и регулярных
  выражениях.
- **Docker-образ не собирался** ([п. 5.5](#55-образ-ни-разу-не-собирался--как-проверить)).

### Метрики и что они значат

- Все метрики посчитаны на **обучающих** объектах (15 эталонных проверок организаторов): Precision 1.00, Recall 0.80,
  F1 0.89, FPR 0.
- Официальную оценку организаторы считают по **закрытой** разметке тестового объекта (Речников). Она будет другой.
- Подробности — в документе для презентации.

## 16. Частые вопросы

**Можно ли делать интерфейс, не запуская ML?**
Да. В репозитории лежат настоящие ответы по трём объектам (`out/submission_*.json`) и отчёты целостности
(`out/integrity_*.json`). Документы для картинок страниц — из пакета организаторов.

**Почему строк больше 132?**
У некоторых параметров несколько мест: конструкции, помещения, этажи. Каждый из 132 параметров присутствует хотя бы
одной строкой.

**Почему так много «сравнить нельзя»?**
Большинство — заглушки: для параметра нет извлечения. Отличайте их по пустым `evidence` и значениям ([п. 7.5](#75-violation_label-метки)).

**Почему у Речникова всего один кандидат?**
На тестовом объекте почти всё сверенное совпало. Трек вентиляции, который дал 8 кандидатов на обучающей Тюменской,
на Речникове не работает: в его РД нет комплектов ОВ. Система настроена «лучше промолчать, чем ошибиться».

**Можно ли передать ML папку с PDF без реестра?**
Нет. Стадия, раздел и `file_id` берутся из реестра ([п. 3.5](#35-если-объект-загружают-через-интерфейс-что-должен-сделать-backend)).

**Нужен ли GPU?**
Для `ml.run` сейчас — нет. GPU понадобится, если в прогон встроят OCR сканов.

**Что будет, если упадёт один трек?**
Остальные отработают, ответ запишется, на месте упавшего трека будут заглушки, в stderr — трассировка.

**Пересчитывать ли ответ после обновления ML?**
Да, `ml.run` по каждому объекту. Формат не меняется, могут добавиться строки.

**Откуда номер страницы — с 0 или с 1?**
С 1: как в просмотрщике PDF. В PDF.js `getPage()` тоже нумерует с 1.

| **РД** | рабочая документация: по ней строят. Дробится на комплекты по маркам (АР, КЖ, ОВ, ВК, ЭОМ…) |
| **ИД** | исполнительная документация: акты о том, что построено (АОСР — акты освидетельствования скрытых работ). Почти всё — сканы |
| **Матрица** | 132 параметра, которые надо сверить между стадиями, с источниками и триггерами (`parameter_catalog_132.jsonl`) |
| **Триггер** | условие нарушения из матрицы: «понижение класса бетона», «уменьшение толщины»… |
| **Кандидат** | найденное расхождение с доказательствами (`VIOLATION_PRESENT`). Нарушением его делает инспектор |
| **Шифр** | обозначение документа в штампе: `01-07-22-14-П-КР1` (объект, стадия П / РД, марка) |
| **Редакция** | «Изм. 2», «кор3» — версия документа внутри своей стадии. Сравнивать можно только с действующей |
| **Текстовый слой** | текст внутри PDF, который можно выделить мышью. У сканов его нет |
| **OCR** | распознавание текста на картинке (сканы, подписи-линии на чертежах) |
| **bbox** | прямоугольник фрагмента на странице |
| **CropBox, MediaBox, Rotate** | размеры и поворот страницы в PDF; из-за них координаты в файле ≠ координатам на экране |
| **Экспликация** | таблица помещений на плане: номер, назначение, площадь |
| **Заглушка** | строка ответа для параметра, по которому нет извлечения |
| **Обучающие объекты** | Новослободская и Тюменская: по ним есть публичный эталон организаторов (15 проверок) |
| **Тестовый объект** | Речников ул. 7-7: по нему считают официальную оценку, разметка закрыта |
