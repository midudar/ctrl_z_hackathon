This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за проект

Хакатон ЛЦТ, кейс №10 «Мосстройнадзор» — сервис «Инспектор ИИ». Он сверяет три стадии документации одной стройки по матрице из 132 параметров:
- **ПД** — проектная документация (что обещали, утверждена экспертизой);
- **РД** — рабочая документация (по ней строят);
- **ИД** — исполнительная документация (акты о том, что построено).

Система **не выносит вердикт**. Она готовит кандидата в нарушения с карточкой доказательств (файл, страница, значения), а подтверждает нарушение инспектор. Это требование ТЗ, и оно отдельно оценивается.

Полное ТЗ — `10. Мосстройнадзор.pdf` (редакция 1.1). Где что искать:
- раздел 1.5 — предписанный стек: React, Node.js, Python 3.11+, REST и RabbitMQ;
- раздел 9.1 — требования к парсингу: OCR, Sentence-BERT `all-MiniLM-L6-v2`, CV по размерной линейке, bbox в [0;1] с учётом CropBox и Rotate, кеш в Redis;
- раздел 9.2 — статусы протокола; там же ссылка на Приложение 2: образец протокола **обязателен для исполнения** (см. «Архитектура пайплайна», этап 5);
- раздел 11 — нормативы скорости (см. «Текущее состояние»);
- раздел 14 — метрики приёмки.

**`ТЕХНИЧЕСКОЕ ЗАДАНИЕ НА РАЗРАБОТКУ СЕРВИСА.docx` в `01_ПАКЕТ/…/00_ТЗ_И_ПРИЛОЖЕНИЯ/` — устаревшая редакция 1.0**
(статусы OK / WARNING / CRITICAL, Tesseract или Amazon Textract, автоматическое дообучение, «частично подтверждено»).
Требования брать только из PDF ред. 1.1; тот же PDF лежит в `ТЗ.zip` (SHA-256 совпадает). Из ред. 1.0 в схему
ответа попало поле `protocol_status`.

### Трек ОВ (`rooms.py`) — чертежи по помещениям

Как работает:
1. Чертёжные листы отбираются автоматически (`drawing_pages`: лист шире 1000 pt и ≥ 5 номеров помещений). Файлы ОВ по стадиям пока заданы руками в `DRAWING_FILES` (перевести на `registry.py` — задача из очереди).
2. Токены страницы = текстовый слой + OCR. **Подписи на чертежах РД нарисованы линиями (шрифт ISOCPEUR из CAD) и в текстовом слое отсутствуют, поэтому OCR нужен и для векторных чертежей.** Если OCR листа нет в кэше, берётся только текстовый слой и печатается предупреждение: тяжёлый OCR локально не запускается.
3. Марка → помещение: ближайший номер, до которого есть «прямая видимость» без пересечения стены; если её нет — идём по выноске и ищем от её конца. Номера из колонок экспликации отбрасываются; «267, 270» — одна подпись-группа (`room_group`).
4. Сравнение по помещению: система ПД отсутствует в РД → `MISSING_DESIGN_ELEMENT`; система есть, но ни одна ветка не совпала → `CONFIGURATION_MISMATCH` (надёжно только при ≥ 2 ветках с каждой стороны).
5. Ключевые элементы (`KEYWORD_ELEMENTS`, пока «тёплый пол» → `FREE-HEATING-001`): от подписи прослеживаются все выноски, у их концов ищется помещение. Если в РД элемент не упоминается нигде (текст + OCR) — кандидат; если упоминается, но не у этого помещения — `COMPARISON_IMPOSSIBLE`.
6. Лист-доказательство: страница, где лежат именно расходящиеся системы. Для ключевых элементов лист РД выбирается по теме элемента в штампе (штампы РД тоже нарисованы линиями, OCR читает их с латинскими двойниками: «OmonлeHue» = «Отопление»).

**Слои CAD.** `get_drawings()` отдаёт слой каждого элемента (pymupdf 1.28). Стены лежат на `ОВ-Архитектура`, `Монолит`, `S_перегородки`, `A-DOORS`, выноски на `…-Выноски`, подписи систем на `DUCT-…-TEXT`. `page_geometry()` (кэш) берёт стены и выноски по слоям (`WALL_LAYER_RE`, `LEADER_LAYER_RE`), если их хватает (≥ 200 отрезков стен), иначе прежние эвристики (на листах ПД стены по-прежнему эвристикой). При выносках со слоя включается «выноска первой» и до 8 шагов по ней. Для ключевых элементов выноски берутся из обоих источников (`leaders_any`): у тёплого пола выноска не на слое выносок. Слои есть у Речникова в 57 из 89 PDF ПД и 18 из 44 PDF РД.

**Страховка «установка перемещена»** (`MOVED_SAFETY`): если хотя бы половина «пропавших» у помещения систем — целые установки (марки без ветки: П4, ПД19), которые на чертежах РД есть у другого помещения, ставится `COMPARISON_IMPOSSIBLE`. Ветки (В2.7) правило не трогает, поэтому 140/142 сохраняются.

**Результат на Тюменской (26.09, после полок выносок): P 1.00, R 0.80, F1 0.89, локализация 0.80, 8 кандидатов, все совпадают с эталоном, вне разметки 0.** Находятся 140, 142 (пропала вытяжка В2), 147, 198 (другие ветки В2), тёплые полы 267/270/271/272. Пропущены: 012 (снята страховкой), 314 (в РД одна ветка В3.1 из двух — см. ниже). До 26.09: R 0.70, F1 0.82, 147 — «сравнить нельзя».

Главная слабость — привязка подписей к помещениям на **планах РД**. Со слоями заметно лучше, остаются ошибки OCR и несовпадение нумерации помещений ПД/РД.

**Полки выносок (26.09, `shelf_anchor`, флаг `USE_SHELVES`) — подняли Recall 0.70 → 0.80 и F1 0.82 → 0.89.**
Сначала попытка была отклонена: 147 (ПД В2.10 — одна ветка | РД В2.3, В2.4) находится, если требовать ≥ 2 веток только в РД,
но тогда появлялся ложный **168** (ПД В17.13 | РД В17.9, В17.11). Проверено глазами: «В17.13» в ПД стоит над коридором 168,
а выноска ведёт к клапану в горячем цехе 189; в 314 так же — «В3.1», «В3.2» над стеной 313 / 314, выноски — к установкам
в 314. **Причина общая:** на листах ПД (`F0171` стр. 85–88) слой «ОВ-Вентиляция-Выноски» есть, но на нём только белые маски под
текстом (≥ 10 отрезков — слой считается настоящим), а сами выноски лежат на слое «0»; `follow_leader` находил край маски и
сдавался. **Правило по ГОСТ 2.316:** подпись стоит на полке (горизонтальный тёмный отрезок у нижнего края текста, под ≥ 60%
его ширины, не длиннее 2,5 ширины + 30 pt), к концу полки примыкает **наклонная** линия (10°–80°, один шаг — цепочки по
отрезкам уходили по стенам и стоякам) → подпись относится к помещению у её дальнего конца. Порядок: выноски со слоя (как
раньше) → полка → прямая видимость → выноска-эвристика → ближайший номер. После этого «≥ 2 ветки только в РД» больше не
даёт 168 (В17.13 ушла в 189), и 147 находится с эталонными страницами. Контроль: без полок то же ослабление снова даёт 168.
В РД правило перепривязало марки у ~85 помещений; выборочно проверено глазами — верно:
шесть стояков (В6.1, В6.3, В1.1, В1.2, В10.4, В12.1) стоят в углу 249, а раньше уходили к 202 за стеной; «В3.1» в РД — к
воздуховоду в 314. На эталон влияет только 147; в ответе Тюменской ушли «сравнить нельзя» у 131, 168, 259, 301, появились
у 189, 191, 341. Тестовый объект не затронут (в РД Речникова ОВ нет, трек ОВ по нему не запускается).
Оговорка: правило отлажено на тех же 10 нарушениях, по которым считаются метрики (другой разметки чертежей ОВ нет).

Что осталось (локализация 0.80 — по всем 10 нарушениям, для 0,95 нужны все 10):
- **314:** в ПД у помещения теперь В3.1 и В3.2, в РД — одна В3.1 (−600 м³/ч, `F0201` стр. 20). Одна ветка совпала, а правило
  «конфигурация изменена» ловит только полную замену веток. Правило «ветка ПД пропала в РД» было бы новым критерием,
  проверить его не на чем, кроме этого же примера, — не делаем.
- **012:** в РД у помещения добавлены установки (П21, П19, П12) — правило «лишние установки» по-прежнему неотличимо от 006.

**Урок 21.09:** первая версия гнала все 10 342 полосы одной ячейкой и выгружала результат только в конце.
Связь VS Code с Colab оборвалась на 3000 (вывод застыл, кнопка ■ не работала, «Перезапустить ядро» в VS Code

Почему такие параметры (замер 21.09 на актах Новослободской): при 90 dpi JPEG «Реестр приложений» не распознавался;
120 dpi в чёрно-белом PNG (порог Оцу) читается и весит 5–12 КБ на полосу против 40–60 КБ у JPEG. «Реестр
приложений» стоит на ~9% высоты страницы, заголовок «АКТ освидетельствования скрытых работ» — на ~38%, в самом
верху бланка — «Объект капитального строительства». Мелкий текст в полосе шумит, но для типа страницы нужны
только заголовки. Точность определения типа проверять на Новослободской: там у бланков и реестров есть текстовый
слой, это эталон. На Речникове правила не подбирать.

**Тип страницы (`ml/page_kinds.py`, проверено 22.09 на Новослободской).** По тексту полосы страница относится
к одному из типов: `act` (бланк АОСР), `register` (реестр приложений), `quality` (документ о качестве бетонной
смеси), `protocol`, `certificate`, `scheme`, `other`, `empty`. Эталон — тип по текстовому слою той же верхней
части страницы, сверка на 423 страницах с текстом: **совпало 0.94; бланки актов 226 из 226, ни одной чужой
страницы (точность и полнота 1.00); документы о качестве 8 из 8**; путаются только сертификаты и реестры
приложений к ним, для извлечения они не нужны.
**Состояние на 23.09 (вечер): забрано 7 868 полос из 10 342** — вся Новослободская (2 018) и 5 850 по Речникову
(порции 1–9: `F0205`–`F0222` целиком, `F0223` до стр. 290) — **все папки по монолиту, кроме `F0224` (ПП рампы,
24 стр.) и `F0230` (папка 33, АООК лестничных клеток)**. Порции 10–13 решено не гонять: там электрика, отделка, кладка
и металл, для текущих проверок (класс бетона и арматуры) они не нужны. Скорость на T4 — 0,76–1,03 с на полосу,
порция из 650 полос — 8–11 минут. По распознанным папкам монолита бланки актов, реестры и документы о качестве —
около 30% страниц (бланки и реестры — около 15%).

**Проход по Речникову (22.09, 2 600 полос из 8 324).** Бланки актов на сканах находятся: 162 бланка,
194 документа о качестве бетонной смеси, 127 реестров; в файлах по монолиту (этажи, вертикальные конструкции,
плиты перекрытий) бланков по 6–39 на файл, там же документы о качестве. Скорость порции — около 0,8 с на полосу.
При этом всплыла ошибка, которой на Новослободской не видно: **сертификаты соответствия принимались за бланки
актов** («…на выполнение работ по оценке соответствия…»). Поэтому признаки бланка теперь требуют, чтобы слова
шли подряд (`_phrase`), и либо сильного признака («освидетельствование»), либо двух слабых из `ACT_WEAK`
(поля бланка: застройщик, технический заказчик, предъявлены документы, разрешается производство…).
После правки на Новослободской бланки 221 из 223, общая точность прежняя; у Речникова «бланков» стало 162
вместо 220.

Три правила, без которых не работает:
1. **Сравнение слов нечёткое** (`SequenceMatcher`, порог 0.78): OCR полосы даёт «Объскт кяпитального
   строитсльства», «докумснтяции», «Прн выполнснин рябот примснсны». Из-за последнего якорь по слову
   «применены» не проходит порог — берётся «работ».
2. **Бланк акта проверяется первым:** его вторая страница сама перечисляет «Исполнительную схему»,
   «Протокол испытаний» и «Реестр приложений №1», и страница уезжала в эти типы.
3. **Слова признака идут подряд** (`_phrase`), иначе сертификаты становятся актами (см. выше).
Отдельно: «документ о качестве» требует слова «смеси» — у металла свой «сертификат качества», он не нужен.

`page_room_systems(..., trace=[])` возвращает в `trace`, какая подпись к какому помещению отнесена: нужно для карточек и отладки привязки.

### Выбор актуальной редакции (`revisions.py`)

Рядом с томом лежат и его корректировки: `01-0722-14-П-КР1.pdf` (2022), `…-КР1-кор2.pdf` (2024),
`01-07_22-14-П-КР1-кор3.pdf` (2025). Без отбора значения и ссылки-доказательства берутся из вперемешку
старых и новых редакций, а по ТЗ сверять можно только с последней утверждённой.

- **Группировка по шифру.** Из имени файла убираются маркер редакции и «(1)» (копия при скачивании),
  остальное сводится к буквам и цифрам: один шифр пишут как `01-07-22-14-П`, `01-0722-14-П`, `01-07_22-14-П`.
- **Номер редакции берётся с титульного листа** («Корректировка №3», год издания), имя файла — запасной
  вариант. Это важно: у `01-07_22-14-П-ИОС7.1-кор3.pdf` на титуле стоит «Корректировка №4». Титул читается
  текстовым слоем у 68 файлов из 69, OCR не нужен.
- Файл без маркера — первая редакция (у Речникова это всегда 2022 год). «Корректировка» без номера на
  титуле → берём номер из имени (`ОПЗ Изм 2` = 2).

### Как устроены документы

Сравнение идёт **по строке «дисциплина × стадия»**, а не внутри одного файла: том ПД про вентиляцию (`ИОС5.4`) ↔ комплекты РД `ОВ1`, `ОВ2.1` ↔ акты ИД по вентиляции.
- **ПД** разбита на разделы по ПП РФ №87 (ПЗ, СПЗУ, АР, КР, ИОС1–5, ПОС, ООС, ППМ, ОДИ, ЭЭ). Внутри тома: титул → содержание → текстовая часть → графическая часть; спецификации лежат рядом со своими чертежами.
- **РД** дробится мельче, по маркам (ГП, АР0…АР4, КЖ0, КМ, ОВ1, ВК, ЭОМ). Внутри комплекта: общие данные (ведомость листов, таблица изменений) → чертежи → спецификация, часто отдельным документом с суффиксом `.С`. Рядом бывают `DWG.7z` и `.docx`. У Речникова в РД 38 архивов (532 DWG, 6 PDF, 17 DOCX) — это исходники тех же комплектов: PDF есть у каждого комплекта (проверено 23.09), поэтому пайплайн по PDF ничего существенного не теряет. DOCX рядом с КЖ — короткие описания ревизий РД (например, ревизии В и С). Содержимое архивов без распаковки показывает встроенный `C:\Windows\System32\tar.exe -tf` (bsdtar: zip, 7z, rar); 7-Zip на ноутбуке не найден.
- **ИД** — не том, а десятки отдельных актов (АОСР, АООК), исполнительных схем и журналов, сгруппированных по этажам, видам работ и месяцам. Почти всё — сканы.

Идентификация документа:
- **Шифр** (`АНО/150321/1-П-ИОС5.4.2`) = объект + стадия (`П` / `РД`) + раздел или марка. Источник истины — штамп в правом нижнем углу листа (ГОСТ Р 21.101), а не имя файла.
- **«Изм. N» / «корN»** — номер редакции документа внутри **своей** стадии. К отличиям ПД↔РД отношения не имеет. Используется только для выбора актуальной редакции: в ПД Речникова рядом лежат `ОПЗ.pdf`, `ОПЗ Изм 2.pdf`, `ОПЗ-кор3.pdf`. Сравнивать можно только с последней утверждённой; конфликт редакций → `CLARIFICATION_REQUIRED`.
- **Лист ≠ страница PDF.** Лист 26 тома ИОС5.4.2 лежит на странице 104.

## Архитектура пайплайна

Задуманная целевая схема. Что из неё уже сделано — в разделе «Команды» выше (`ml/`); `pipeline_demo.py` в корне — первый прототип на одной паре листов, он устарел и оставлен только для демонстрации идеи. Вход — папка объекта с ПД / РД / ИД. Между этапами передаются файлы, так что этапы можно писать и перезапускать независимо.

0. **Реестр → `registry.jsonl`.** Обойти все файлы объекта. Мусор (`.bak`, `.dwl*`, `~$*`, точные дубли по SHA-256) отбросить; архивы распаковать; `.docx` конвертировать; DWG пока вне скоупа. Для каждого файла: SHA-256, стадия, дисциплина/марка, шифр, редакция, статус утверждения. Стадию брать из шифра (`-П-` / `-РД-`), затем из `document_manifest.jsonl`, и только потом из имени папки: у Тюменской РД и ИД лежат в одной папке. Шифр и редакцию брать из штампа, имя файла — запасной вариант (`Изм 2`, `кор3`). Актуальная редакция выбирается **внутри группы с одним шифром**, а не глобально. Для ИД берутся все файлы: акты не заменяют друг друга. Конфликт редакций → `CLARIFICATION_REQUIRED`.
1. **Чтение страниц → кэш `cache/{sha256}/{page}.json`.** Решение «текст или OCR» принимается **для каждой страницы**, а не для файла (в РД ОВ1 страницы 1–31 с текстом, 32–172 — сканы). Результат — единое представление `{tokens: [{text, bbox, conf}], paths, source, kind, stamp}`: вектор читается через `get_text("words")` + `get_drawings()`, скан — через OCR (движок выбирать замером на `ocr_pilot_20260811`). Там же: тип страницы (текст / таблица / чертёж / титул), поля штампа (шифр, номер листа, изм) и нормализация (NFC, кириллица↔латиница, bbox в [0;1] с учётом Rotate / CropBox).
2. **Извлечение → `records.jsonl` (или SQLite).** Матрица задаёт маршрут: по `source_pd/rd/id` понятно, в каких документах и на каких типах страниц искать параметр. Три экстрактора пишут записи одного вида `{object_id, parameter_code, location, stage, шифр, изм, file_id, page, лист, value, raw, conf, extractor}`:
   - таблицы (спецификации, ТЭП, экспликации, ведомости) — первыми, это самый надёжный источник: `find_tables()` на векторе, OCR + сетка на сканах;
   - текст: regex + семантические якоря (Sentence-BERT `all-MiniLM-L6-v2`);
   - чертежи: номера помещений и марки систем с координатами, привязка подписей к помещениям.
3. **Связывание.** Группировка записей по `(parameter_code, location)`. Для чертёжных параметров — сопоставление листов ПД↔РД по пересечению номеров помещений: минимум 3 общих, ранжирование по размеру пересечения, ничьи разрешаются номером листа из штампа (не сделано). Здесь же сценарий загрузки из ТЗ 9.2 (`FULL`, `PD_RD_ONLY`, …) и применимость параметра.
4. **Сравнение** — числовое (порог из `trigger`, с нормализацией единиц), множественное (set ПД vs set РД) или наличие/отсутствие. Перед вердиктом — страховки: контроль полноты извлечения (если на одной стадии найдено в разы меньше элементов, сейчас порог 0.25 → `COMPARISON_IMPOSSIBLE`) и уверенность OCR в зоне доказательства.
5. **Выход.** `submission.json` строго по `submission_schema.json` и протокол для инспектора: карточка на каждого кандидата с обеими страницами и подсветкой. Протокол — **по образцу Приложения 2** (ТЗ 9.2: образец обязателен): 1) статус загрузки ПД / РД / ИД (загружено из ожидаемого); 2) сводная статистика с процентами; 3) параметры, не проверенные из-за отсутствия ИД (код, раздел, параметр, какого файла нет); 4) критические и 5) существенные нарушения (раздел, параметр и код, значения ПД / РД / ИД, отклонение, решение инспектора); 6) подозрения ИИ (метод, описание, решение, причина отклонения, комментарий ИИ); 7) резолютивная часть — конкретная рекомендация по каждому нарушению.

Дополнения к этапам (согласованы 19.09):
- **Этап 1: сначала дешёвый проход, потом полный OCR.** Полный OCR всех сканов не успеет: 8 864 страницы × 1–3 с на CPU — это часы, а ТЗ требует ≤ 10 мин на 500 страниц. Поэтому сначала низкое разрешение и только штамп с заголовком: получаем шифр, лист и `kind`. Полный OCR — только для страниц, нужных по матрице (спецификации, ТЭП, экспликации). `kind` определяется **до** полного OCR.
- **`location` зафиксировать до извлечения.** Для каждого параметра (типа параметра) задать формат `location` и функцию нормализации. Экстракторы пишут `location` уже в этом формате. Ошибка в `location` = находка не засчитана.
- **Этап 5: в ответе все 132 параметра.** Пройти по всей матрице. Если параметр не извлечён, ставим `MISSING_DOCUMENT` или `COMPARISON_IMPOSSIBLE`, но строку не выбрасываем: эти метки не штрафуются как ложные, а пропуск критической точки ограничивает итог 59. Критические параметры покрываем первыми. (Раньше здесь было «за комплектность 10 баллов» — это неверно, см. «Формат ответа и скоринг».)
- **ИД сравнивается иначе, чем ПД↔РД.** В ИД значения чаще не повторяются, а подтверждаются: есть ли акт на вид работ и этаж, совпадает ли в нём материал или марка с РД. В основном это сравнение «есть / нет» плюс поиск акта по виду работ и этажу.
- **Статус утверждения** из PDF надёжно не достать. Считаем утверждённой последнюю редакцию; `CLARIFICATION_REQUIRED` ставим, только когда штамп и имя файла противоречат друг другу.

Проверка качества:
- Итог: прогон на обучающих объектах (Новослободская, Тюменская), сверка с `public_gold_checks.jsonl` из TRAIN-архива → Precision / Recall / F1. Тестовый объект для подбора правил не использовать.
- Отдельные проверки на каждый этап, потому что по 10 проверкам F1 не показывает, какой этап сломался. Этап 0: шифр и стадия против `document_manifest.jsonl`. Этап 1: Character Accuracy на `ocr_pilot` (он же нужен для порога ТЗ ≥ 0,95). Этап 2: 20–30 значений с обучающих объектов, вбитых вручную.

Порядок работы: (1) формат `location` и скелет ответа на все 132 параметра; (2) этап 0 + проход по штампам; (3) таблицы на векторных страницах по размеченным параметрам и замер F1; (4) OCR отобранных сканов; (5) текст, ИД, чертежи.

Модели обучать не на чем: 15 размеченных проверок (10 нарушений по 3 кодам на Тюменской + 5 отрицательных на Новослободской), `training_eligible_labels: 0`. Готовые модели (OCR, Sentence-BERT) используются, свои не обучаются. Решение о расхождении принимают правила из матрицы.

## Формат ответа и скоринг

Ответ — JSON по `submission_schema.json`: `object_id` + `checks[]`, в каждой проверке `parameter_code`, `location`, `violation_label`, `evidence[{stage, file_id, pdf_page_number}]`.
- `violation_label` ∈ `VIOLATION_PRESENT`, `NO_VIOLATION`, `MISSING_DOCUMENT`, `COMPARISON_IMPOSSIBLE`. Последние два не штрафуются как ложные срабатывания — это законный способ промолчать.
- В ТЗ (раздел 9.2) своя система статусов протокола. Для файла ответа её переводим так:

  | Статус ТЗ | `violation_label` в ответе |
  |---|---|
  | `CANDIDATE` (нашли расхождение с доказательствами) | `VIOLATION_PRESENT` |
  | `NEGATIVE_VERIFIED` (сверили, расхождения нет) | `NO_VIOLATION` |
  | `MISSING_EVIDENCE` (нет обязательного документа или фрагмента) | `MISSING_DOCUMENT` |
  | `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED` (источники несопоставимы, конфликт редакций) | `COMPARISON_IMPOSSIBLE` |
  | `NOT_APPLICABLE`, `SUSPICION` | в `checks` не выводим |

  `CONFIRMED_VIOLATION` ставит только инспектор в интерфейсе, система сама его не присваивает.
- Сопоставление с эталоном по ключу `object_id` + `parameter_code` + `location`. Неверный `location` = находка не засчитана.
- Локализация оценивается как точное совпадение файла и страницы; bbox в скоринге не нужен.
- Коды параметров брать из датасета (`PZ-001`, `SPZU-027`, `IOS4-079`). В матрице ред. 1.1 есть параллельная нумерация `M-001…M-132` с теми же номерами — в ответе её не использовать. Содержание трёх версий матрицы — Приложение 1 в пакете, ред. 1.1 из `ТЗ.zip` и `parameter_catalog_132.jsonl` — совпадает дословно (сверено 23.09 по всем 132 строкам); отличаются только коды и подпись приоритета: «Критическое» = HIGH, «Существенное» = MEDIUM.
- Поле `criticality` заполнять формулировкой из датасета («Критическое (приостановка работ)»), а не `HIGH/MEDIUM` из матрицы 1.1.
- **Критических параметров 106 из 132**, существенных 26. Поэтому почти любое пропущенное нарушение из скрытой разметки включит потолок 59.

Судейская доска ЛЦТ — 20 баллов, проходной 12. На качество моделей приходится около 8 баллов; остальное — функциональность, доказательность, техготовность и удобство. Неработающий прототип получает не больше 6 баллов и не допускается в финал. Технический скоринг — 100 баллов, источник — `02_МЕТОДИКА/hackathon_gold_20260811/УЧАСТНИКАМ_БЕЗ_ОТВЕТОВ/data/scoring_summary_without_answers.json`: `finding_detection_f1` 60, `source_localization_exact_file_page` 15, `normalized_value_and_status_accuracy` 15, `document_integrity_and_split_handling` 10; «при пропуске любой утверждённой критической контрольной точки итоговый балл ограничивается 59». **Последние 10 баллов — не «все 132 строки в ответе»**, а целостность документов и обработка разбиения; точный смысл не раскрыт (вопрос организаторам). `split_policy.json` исключает файлы `F0149`, `F0418` — их нет в реестре, код их и так не читает.

**Что именно оценивают (ТЗ 14.1–14.3).** Единица оценки — `evidence_group`: объект + параметр или атомарное правило + сопоставимые актуальные редакции + доказательства. P/R/F1 считаются по группам **скрытой разметки**, а не по всем 132 параметрам; совпадение требует верного параметра (типа расхождения) и верного доказательства. В скрытом тесте обязательно есть пять классов: подтверждённые нарушения, проверенные отрицательные группы, отсутствующие доказательства, неприменимые параметры и **конфликт редакций**. FPR считают на `NEGATIVE_VERIFIED` **и на случаях с устаревшей редакцией** — отбор редакций (`revisions.py`) напрямую влияет на оценку. Метрики публикуются отдельно по разделам и типам нарушения; при недостижении любого порога система не принимается, даже если сводная F1 выше. Пороги ТЗ: Precision ≥ 0,90, Recall ≥ 0,80, FPR ≤ 0,10, OCR Character Accuracy ≥ 0,95, Exact Match ключевых полей ≥ 0,90, связка документов ≥ 0,95, локализация ≥ 0,95 групп (файл и страница, bbox с IoU ≥ 0,5).

## Известные ловушки данных

- **Сканы.** В тестовом объекте 8 864 страницы из 16 078 без текстового слоя (в обучающих — 388 из 10 146). В РД ОВ1 страницы 32–172 — сплошной блок сканов, среди них спецификация оборудования (`АНО/150321/1-РД-ОВ1.С`).
- **Где лежат параметры.** По полям источников матрицы: около 65% параметров ищутся на чертежах, 63% в таблицах, 20% в тексте (многие сразу в нескольких местах). Таблицы — самый надёжный источник. Например, `IOS4-079` матрица велит брать из спецификации, а не с чертежа.
- **Подписи на чертежах РД — это линии, а не текст.** Шрифт ISOCPEUR из CAD экспортирован контурами, в текстовом слое подписей нет. Поэтому «3 марки против 20» — не проблема регулярки, а отсутствие текста: нужен OCR даже для векторных листов (решено в `pages.py`). Сами подписи бывают через запятую (`П8, П18`), с суффиксами (`П17.1`, `П18/ККБ`) и на длинных выносках далеко от помещения (разбор — в `marks.py` и `rooms.py`).
- **Кириллица и латиница.** «В25» (класс бетона) и марка «В2» распознаются то кириллицей, то латиницей; арматура в ПД «А500C» латиницей, в РД «А500С» кириллицей. OCR курсивных штампов даёт «OmonлeHue» вместо «Отопление». Нормализация нужна везде (`marks.py`, `concrete.py`, `_ITALIC2CYR` в `rooms.py`).
- **Геометрия чертежей.** CAD экспортирует линии мелкими отрезками (медиана 1.1 pt), замкнутых контуров нет; стены в РД идут кусками по 90–96 pt. Спасают **слои CAD**, сохранённые в PDF: стены и выноски берутся по имени слоя (см. трек ОВ). Где слоёв нет — работают эвристики по цвету и длине.
- **Один и тот же текст на разных листах устроен по-разному.** На A4-записках конструкция и значение — две колонки одного ряда; на листах A1 склейка по горизонтали смешивает разные блоки чертежа. Поэтому склейка рядов в `concrete.py` включена только для листов не шире 700 pt.
