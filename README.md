# Инспектор ИИ

_Команда `ctrl_z` · ЛЦТ 2026, кейс № 10 «Мосстройнадзор»._

Сервис для инспекторов Мосгосстройнадзора. Он сверяет три стадии документации объекта капитального строительства
по матрице из 132 параметров и готовит протокол по образцу Приложения 2 к ТЗ:
- **ПД** — проектная документация, утверждена экспертизой;
- **РД** — рабочая документация, по ней строят;
- **ИД** — исполнительная документация, акты о том, что построено.

Система **не выносит вердикт**. Она находит **кандидатов в нарушения** и прикладывает доказательства: файл, страницу,
подсвеченный фрагмент и значения на каждой стадии. Нарушением запись становится только после решения инспектора.

![Карточка кандидата: значения ПД / РД / ИД, страницы-доказательства с подсветкой, решение в 1–3 клика](ml-service/docs/img/ui_review.png)

## Запуск в Docker

Нужны Docker Engine 24+ с Compose v2 (Docker Desktop или Docker в Linux), 4 ГБ свободной памяти и около 3 ГБ на диске
(образы — 1,3 ГБ). GPU не нужен.

```bash
git clone https://github.com/midudar/ctrl_z_hackathon.git
cd ctrl_z_hackathon
cp .env.example .env
docker compose up --build
```

Откройте http://localhost:8080 и войдите как `inspector` / `inspector`.

Перед `docker compose up` желательно сделать ещё два шага. Без них сервис тоже работает.

1. **Кэш распознанных страниц.** Скачайте архив `inspector_ml_assets.zip` из
   [Releases](https://github.com/midudar/ctrl_z_hackathon/releases) и распакуйте его в `ml-service/`: появятся
   `ml-service/out/cache/` и `ml-service/models/easyocr/`. В кэше лежит текст сканов, заранее распознанный на GPU. Без него
   значения со сканов, например из актов ИД, не извлекаются. Всё, что есть в текстовом слое PDF, извлекается и без кэша.
2. **Пакет участника** (документы трёх объектов, которые организаторы выдали всем командам). В `.env` укажите в
   `PACKAGE_DOCS` и `PACKAGE_DATA` пути к папкам `01_ДОКУМЕНТАЦИЯ` и `02_ФОРМАТ_ДАННЫХ_И_ПРИМЕРЫ/data`. Тогда при первом
   запуске на дашборде сразу появятся Новослободская, Тюменская-5 и Речников. Первая версия протокола у них — наши готовые
   ответы ML (`ml-service/out/submission_*.json`), чтобы не ждать прогона. Из пакета берутся только документы и реестр
   файлов, эталонная разметка не используется. Без пакета создайте объект в интерфейсе и загрузите PDF.

| Адрес | Что там |
|---|---|
| http://localhost:8080 | интерфейс инспектора |
| http://localhost:8080/api/docs | Swagger UI; спецификация OpenAPI 3.0 — [`backend/openapi.yaml`](backend/openapi.yaml) |
| http://localhost:8080/api/v1/health, `/api/v1/metrics` | состояние сервиса и метрики Prometheus |
| http://localhost:15672 | панель RabbitMQ (`inspector` / `inspector`) |

Порты, пароли и пути задаются в `.env`. Остановить: `docker compose down`. Начать с чистого листа: `docker compose down -v`,
при этом удаляются база и загруженные файлы.

Если сборка не может скачать базовые образы, значит Docker Hub недоступен из вашей сети. Подключите зеркало
Docker Hub: в `/etc/docker/daemon.json` (в Docker Desktop — Settings → Docker Engine) добавьте
`{"registry-mirrors": ["https://mirror.gcr.io"]}` и перезапустите Docker.

На Windows без Docker Desktop подойдёт Docker Engine внутри WSL2. Скрипт установки —
[`ml-service/tools/wsl_docker.sh`](ml-service/tools/wsl_docker.sh), как его запустить, написано в начале файла.

## Запуск без Docker

Нужны Node.js 22.13 или новее (проверено на 24) и Python 3.11 или новее (проверено на 3.12).

```bash
pip install -r ml-service/requirements-worker.txt
cd frontend && npm ci && npm run build && cd ..
cd backend && npm ci
PYTHON=python3 ML_ROOT=../ml-service \
PACKAGE_DOCS=/путь/01_ДОКУМЕНТАЦИЯ PACKAGE_DATA=/путь/02_ФОРМАТ_ДАННЫХ_И_ПРИМЕРЫ/data npm start
```

Сервис откроется на http://localhost:8080. RabbitMQ в этом режиме не нужен: backend сам запускает Python-воркер
отдельным процессом. На Windows вместо переменных в командной строке создайте файл `backend/.env` с теми же переменными.

## Что посмотреть за 5 минут

1. Войдите как `inspector` / `inspector`. На дашборде объекты раскрашены по состоянию.
2. Откройте объект «Тюменская-5» (8 кандидатов по вентиляции) и нажмите «Начать верификацию».
3. В карточке кандидата значения ПД / РД / ИД стоят рядом, под ними страницы-доказательства с красной рамкой на фрагменте.
   Решения: «Подтвердить» — 1 клик, «Отклонить» — 3 клика (кнопка, причина, сохранить), «Требует уточнения» — 1 клик.
   Работают и клавиши 1 / 2 / 3.
4. Когда у всех кандидатов есть решение, нажмите «Финализировать». Протокол выгружается в PDF, DOCX, XML и JSON.
5. Новый объект: кнопка «+ Новый объект», затем загрузка PDF по стадиям. Проверка запускается сама и идёт
   20–60 секунд на несколько файлов.
6. Войдите как `supervisor` / `supervisor` и откройте «Журнал аудита»: там все действия с временем, IP и причинами.

## Учётные записи стенда

| Логин / пароль | Роль | Что может |
|---|---|---|
| `inspector` / `inspector` | Инспектор | загрузка, проверка, решения по кандидатам, финализация, протокол |
| `supervisor` / `supervisor` | Инспектор-супервизор | то же, плюс отмена финализации и журнал аудита |
| `admin` / `admin` | Администратор | объекты, отмена финализации, журнал аудита, пользователи |
| `ml` / `ml` | ML-инженер | просмотр, полные журналы обработки, решения для дообучения |

Пароли задаются переменными `PASS_INSPECTOR`, `PASS_SUPERVISOR`, `PASS_ADMIN`, `PASS_ML` при первом запуске.

## Как это устроено

```
frontend (React) ──REST──▶ backend (Node.js: API, OpenAPI, роли, аудит, SQLite)
                              │ задача «проверить объект»          ▲ события: ход, готово
                              ▼                                    │
                          RabbitMQ ──▶ ML-воркер (Python) ── ml.run: 8 треков извлечения и сравнения
                                        └─ REST: картинки страниц, протокол PDF / DOCX
```

| Слой | Стек |
|---|---|
| Интерфейс | React 19, React Router 7, Vite 7 |
| Backend | Node.js 24, Express 5, встроенный SQLite (`node:sqlite`), OpenAPI 3.0 (express-openapi-validator, Swagger UI), JWT, amqplib |
| Очередь | RabbitMQ 3.13 |
| ML | Python 3.12, PyMuPDF (текстовый слой, слои CAD, картинки страниц), python-docx, NumPy, OpenCV; OCR сканов — PaddleOCR и EasyOCR на GPU, результат хранится в кэше по SHA-256 файла |
| Запуск | Docker Compose: `rabbitmq`, `ml-worker`, `backend` (backend раздаёт и собранный интерфейс) |

| Папка | Что в ней |
|---|---|
| `frontend/` | интерфейс инспектора: дашборд объектов, загрузка, протокол, карточка кандидата, журнал аудита |
| `backend/` | REST API (`openapi.yaml`), база, очередь, журнал аудита, данные протокола, автотесты (`npm test`) |
| `ml-service/` | ML-часть: пайплайн `ml.run`, воркер `ml/worker.py`, протокол `ml/protocol.py`, образ воркера (`Dockerfile.worker`) и образ для стенда жюри (`Dockerfile`), [README ML-части](ml-service/README.md) |
| `docker-compose.yml` | RabbitMQ, ML-воркер и backend с интерфейсом |

## Образ ML для стенда жюри

Образ ML — отдельный Docker-образ без интерфейса: он обрабатывает объект целиком и пишет `submission.json` в формате
организаторов. Нужен GPU-хост с NVIDIA Container Toolkit; без GPU образ тоже работает, потому что OCR в прогоне не
запускается.

```bash
cd ml-service
docker build -t inspector-ml .
docker run --gpus all -v /путь/01_ДОКУМЕНТАЦИЯ:/input/docs:ro -v /путь/02_ФОРМАТ_ДАННЫХ_И_ПРИМЕРЫ/data:/input/data:ro \
  -v "$PWD/output":/output inspector-ml OBJ-RECHNIKOV-7-7
```

Подробности — в [README ML-части](ml-service/README.md).

## Что проверено

- **Docker:** `docker compose up --build` из чистого клона ветки на Docker Engine 29.1 с Compose 2.40 (Ubuntu 24.04 в WSL2).
  Первая сборка заняла 6,5 минуты, почти всё время ушло на скачивание зависимостей. Все три контейнера проходят
  healthcheck. Проверены оба варианта: с архивом кэша и пакетом организаторов, а также без них (`.env` = `.env.example`).
- **Путь через RabbitMQ:** новый объект, загрузка ПД и РД, проверка за 21 с, кандидат с доказательствами. Дозагрузка ИД —
  новая версия протокола за 18 с с перенесённым решением. Полный пересчёт объекта пакета через очередь дал протокол,
  совпадающий с готовым ответом ML строка в строку. Картинки страниц и протокол PDF / DOCX собирает воркер по REST.
- **Интерфейс в Docker** (Edge): верификация 8 кандидатов за 13 секунд по 1–3 клика и финализация, без ошибок в консоли.
- Автотесты backend: `cd backend && npm test`, 11 тестов. Покрыты вход и права, проверка запросов по OpenAPI, правила
  решений и финализации, журнал аудита, выгрузка протокола и перенос решений между версиями.
- Сквозные сценарии в браузере. Верификация всех кандидатов объекта и финализация. Новый объект из загруженных файлов:
  найден кандидат с доказательствами на трёх стадиях. Дозагрузка с переносом решения.
- Метрики ML на обучающих объектах по 15 эталонным проверкам организаторов: Precision 1.00, Recall 0.80, F1 0.89,
  FPR 0.
